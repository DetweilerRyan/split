# Code design principles: reasons and sources

Where the [code design principles](code-design-principles.md) come from, why they're written the way they are, and the decisions behind their rules. Read this only when changing or questioning a principle. Following them needs nothing from this file.

## The document

- **Asked for on [#110](https://github.com/DetweilerRyan/split/issues/110),** after research in a session on 2026-11-24 into six ideas the code already followed. The owner's choices are [recorded there](https://github.com/DetweilerRyan/split/issues/110#issuecomment-7140900477):
  - **"a code design principles doc that has a read trigger when an agent is reading or writing code. the readmes should largely be treated as overview and as an index with read triggers for each file in it's index".** So the engineering index's "Code style" section, from #83, moved here, and so did this sidecar, which was the index's.
  - **"make all four instructions",** after the six ideas were merged into four, so "that all of the material aspects of each principle be included in the new documentation but i don't want ambiguity to arrise from redundency".
- **Consolidated on [#115](https://github.com/DetweilerRyan/split/pull/115),** at the owner's request to "simplify and consolidate any mentions of these new principles from other docs into the new one". Each general statement now lives here, and the other documents keep their specific rules with a link:
  - **The lookup-table rule** moved from [`crap.md`](crap.md)'s responding steps to principle 3, with its line that a table of plain values is data. `crap.md` keeps the CRAP-specific half: oxCrap counts the move, so it doesn't pass.
  - **[Testing conventions](testing-conventions.md#replacing-external-dependencies)' rule for passing a dependency in** links to principle 1, which asks it of code that decides with no cost clause. Its example, `useActiveIdentity` taking only the provider's `setIdentity`, became principle 1's "only the part the code uses". Its "where it costs little" stays there, for other new code, such as a hook that only wraps the provider. The consolidation first deleted it, which would have dropped that rule without the owner deciding to.
  - **[Code layout](code-layout.md)'s hook rule** gives principle 1 as the reason its hooks take effects as arguments.
- **Not the `code-conventions.md` that #43 turned down** ([types and schemas' sidecar](types-and-schemas.meta.md)). That would have gathered rules; this holds only principles, and each rule stays in the document that owns it, which a principle links to.

## Where each principle comes from

Six ideas, merged where they said the same thing, so each has one home.

| Principle                                          | From                                                                                                                                   |
| :------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------- |
| 1. Essential logic apart from accidental machinery | Functional core, imperative shell; domain-driven design's isolated domain; Out of the Tar Pit's separation of essential and accidental |
| 2. State minimal, immutable and contained          | "Stateless first"; Out of the Tar Pit on state                                                                                         |
| 3. The least powerful construct                    | The rule of least power                                                                                                                |
| 4. Complexity only when a use needs it             | Progressive complexity; essentialism; the owner's "avoid hasty abstractions"                                                           |

- **Functional core, imperative shell:** Gary Bernhardt's [screencast](https://www.destroyallsoftware.com/screencasts/catalog/functional-core-imperative-shell) and his 2012 "Boundaries" talk, and Scott Wlaschin's ["Moving IO to the edges"](https://l-lin.github.io/architecture/functional-core-imperative-shell). Pure logic in the core is tested without doubles, and the shell has too few conditions to need many tests.
- **Domain-driven design:** Eric Evans, [_Domain-Driven Design_](https://www.informit.com/store/domain-driven-design-tackling-complexity-in-the-heart-of-software-9780321125217) (2003), chapter 4, "Isolating the Domain". [Smart UI](https://dev.to/ielgohary/layered-architecture-and-smart-ui-domain-driven-design-by-eric-evans-part-ii-chapter-4-1il7), business logic in the UI, is the failure principle 1's last rule names, and the [ubiquitous language](https://www.martinfowler.com/bliki/DomainDrivenDesign.html) is its naming rule.
  - **Fowler's [anemic domain model](https://www.martinfowler.com/bliki/AnemicDomainModel.html)** reads at first like a case against `src/domain/`'s data and functions. The critique assumes objects carry behaviour; [OO purity isn't required](https://blog.codecentric.de/en/2019/10/ddd-vs-anemic-domain-models), and Scott Wlaschin's _Domain Modeling Made Functional_ (2018) makes types plus pure functions the intended shape. That book is from the session's own knowledge; the search didn't find it. What survives of Fowler's point is the risk principle 1 guards against: domain logic leaking into the shell.
- **Out of the Tar Pit:** Ben Moseley and Peter Marks (2006), after Fred Brooks's "No Silver Bullet" (1986). Essential state and logic are the users' problem itself, everything else is accidental, and mutable state is the largest source of complexity ([summary](https://www.recurse.com/blog/51-paper-of-the-out-of-the-tar-pit), [notes](https://matkosoric.github.io/essay/out-of-the-tar-pit)). Principle 1's test, "would it exist with no React, no Yjs and no network?", is its classification, and principle 2's "don't store a value you can compute" is its rule against accidental state that's derived from other state.
- **Stateless first:** no source names it as a principle. The nearest is stateless service design, as in AWS's [Well-Architected framework](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_mitigate_interaction_failure_stateless.html), which also notes that persistent state remains and most systems are a hybrid. So principle 2 keeps long-lived state in the shell rather than banning it.
- **The rule of least power:** Tim Berners-Lee's [Axioms of Web Architecture](https://www.w3.org/DesignIssues/Principles) (1998), formalised by the W3C Technical Architecture Group as [The Rule of Least Power](https://www.w3.org/2001/tag/doc/leastPower-2006-2-13.html) (2006): the more a language can do, the harder it is to tell what a program in it does. The rule against lookup tables of functions is the owner's, from #81 and #82.
- **Progressive complexity:** Krzysztof Cwalina's ["progressive APIs"](https://learn.microsoft.com/en-us/archive/blogs/kcwalina/book-progress-and-progrssive-apis), and Lea Verou's ["simple things easy, complex things possible"](https://lea.verou.me/blog/2025/simple-easy-complex-possible). It's principle 4's rule to default each option to the simple case.
- **Essentialism:** Greg McKeown's book, as practitioners apply it to software: start simple and evolve ([DZone](https://dzone.com/articles/what-is-essentialism-and-how-does-it-make-software-more-efficient)).
- **Avoid hasty abstractions:** the owner, on [#108](https://github.com/DetweilerRyan/split/pull/108#issuecomment-7138995165): "let's avoid hasty abstractions by isolating and encapsolating early/immature decomposed logic/behaviour locally". It echoes Kent C. Dodds's "AHA programming" and Sandi Metz's "duplication is far cheaper than the wrong abstraction". Both are from the session's own knowledge, not searched.

## Where two principles meet

- **1 over 4 for a business rule** was already [code layout](code-layout.md)'s rule: a business rule goes in `src/domain/` "even when only one component uses it today". Without the precedence, principle 4's "beside its one user" would contradict it.
- **Passing an effect in isn't an injection point.** Principle 1, and testing conventions for other new code "where it costs little", ask for an effect to be passed in as an argument. Principle 4 limits injection points, which swap a whole part. Without that line, a review found three different thresholds for injecting something. `RoomView`'s `parts` are the owner's exception on #93, so they're named as that, not as an example to copy.
- **3 and 4 agree on injection points.** Injecting a part adds both power and complexity, so neither principle adds one before a test or a second caller needs it.
- **Principle 3's lookup-table rule covers every table, not only tables of functions.** The owner's rule, on #81, banned moving branches into a `Map`, object or `Set`, and oxCrap counts both kinds; [`oxcrap.meta.md`](../../scripts/oxcrap/oxcrap.meta.md#lookup-tables-dont-lower-a-score) has the decision. So principle 3's "prefer plain data to code" stops short of replacing branches.
- **Functions over classes is principle 2's,** not principle 3's, though the owner's reason on #81 touches both: "stateful OOP" is about state, and "less dynamic" about power. One home keeps it from being stated twice.

## How the document is written

Researched on [agentpatterns.ai](https://agentpatterns.ai/instructions/) on 2026-11-24, at the owner's request, "to make sure that agents are not overly encoumbered by vegue rules and that as the agent models grow more powerful they remain empowered with clarity from the docs". These are the site's summaries of the studies it cites, not the studies themselves.

- **Principles with a test and a reason, not lists of cases.** From [System Prompt Altitude](https://agentpatterns.ai/instructions/system-prompt-altitude/):
  - the right altitude "tells the agent how to reason, not what to decide for each case";
  - capable models "apply stated reasoning to novel inputs rather than pattern-matching enumerated cases";
  - a vague instruction "gives no real constraint", so the model falls back on its defaults.

  So each principle has a concrete test and its reason in a clause, and none says only "write clean code".

- **Only what an agent wouldn't do anyway.** [Evaluating AGENTS.md](https://agentpatterns.ai/instructions/evaluating-agents-md-context-files/): "remove everything the agent can already infer, and keep only what it cannot". So the document doesn't explain the theory behind each idea, which models know. It says what each means here: the test, the folders, and which principle wins.
- **Few instructions.** The same Altitude page cites instruction-following research (arXiv 2507.11538): "even the best frontier models reach only 68% accuracy at a density of 500 instructions". So the document has four principles and two precedence rules. The detailed rules stay in their own documents, read when their trigger fires.
- **A snippet over a paragraph.** [AGENTS.md Design Patterns](https://agentpatterns.ai/instructions/agents-md-design-patterns/): "One real code snippet demonstrating your project's conventions is more reliable than three paragraphs describing them", written as a correct and a wrong version. Principles 1 and 3 have one each. They use invented names, so they don't copy code that changes.
- **Hard boundaries enumerated, judgment left as principle.** Altitude: "For hard boundaries, enumerate the boundary explicitly even if you also state the principle." The hard boundaries here, no classes, readonly types and the layers, are rules that lint enforces, owned by their documents.
- **Scoped to the code a task touches.** Evaluating AGENTS.md found that agents "treat every instruction as equally important, producing more work without proportional accuracy gains". So the document says not to reshape other code to fit the principles unasked.
- **Every vague word given a test.** A fresh-context review of the first draft found "a thin shell" and "as few decisions as it can" with nothing to check them against. So the shell is now defined by principle 1's own test: a condition belongs there only if it wouldn't exist without the machinery. The same review found two false claims, about oxCrap and about doubles, and five restated rules, which were cut or became links. A second review found that the new "don't store what you can compute" rule contradicted `ReceiptStore`'s cached snapshot, so it now names that exception.
- **Reasons in the document, a clause each.** [Single source of truth](../prose/single-source-of-truth.md#reasons-live-in-a-metamd-sidecar) keeps reasons in sidecars, "beyond a clause where a rule would be unclear without one". A principle is that case: Altitude's point is that the stated reason is what lets a model apply it to a new case.

## Functions, not classes or `this`

- **The owner's reason,** on [#81](https://github.com/DetweilerRyan/split/pull/81#discussion_r4671675741), 2026-11-23: "i'm not a big fan of using stateful OOP when largely pure functional approaches result in simpler and less dynamic and therefore less error prone runtime execution." oxCrap's walks became functions on that pull request; [`oxcrap.meta.md`](../../scripts/oxcrap/oxcrap.meta.md) records what that cost.
- **The owner's decision,** on [#83](https://github.com/DetweilerRyan/split/issues/83#issuecomment-7122175097), 2026-11-24: "a small local oxlint JS plugin, with no new dependency, that bans classes, except `Error` subclasses, and `this`", and "Convert all but ReceiptStore". oxCrap's `Run` and both screenplay `Actor`s became functions in the same change.
- **Why a local plugin:** none of oxlint's built-in rules bans every class or every `this`: `max-classes-per-file` allows one per file, `oxc/no-this-in-exported-function` covers exported functions only, and oxlint has no `no-restricted-syntax`; and [`eslint-plugin-functional`](https://github.com/eslint-functional/eslint-plugin-functional) would be a new dependency, which the owner ruled out. The plugin is two rules of a few lines each, written against oxlint's [JS plugin API](https://oxc.rs/docs/guide/usage/linter/writing-js-plugins.html), which is alpha and the repository's first use of it. If a release of oxlint stops loading it, `scripts/lint/functional.real.test.ts` fails.
- **What counts as an `Error` subclass:** a class whose `extends` is a name ending in `Error`, either alone (`Error`, `RangeError`) or as the last part of a dotted path (`errors.ConfigError`). Anything else, such as `errors[name]` or `mixin(Error)`, is reported, since the rule can't tell what it names.
- **`this` is allowed inside a class, and only there,** through `functional/no-this`'s `allowInClasses` option, which `.oxlintrc.json` turns on. The owner chose it on [#103](https://github.com/DetweilerRyan/split/pull/103#issuecomment-7136861369), 2026-11-24, over a block disable for `ReceiptStore`. Since `functional/no-classes` already bans every class but an `Error` subclass and an approved one, a `this` can only read a class that's allowed to exist. That includes an `Error` subclass, which the first version banned `this` in too, on the stricter reading of the owner's words on #83; oxCrap's `ParseError` and `ConfigError` still use none.
  - **What "reads its class" means:** the scope the `this` binds to is a class's method, constructor, accessor, field value or static block. An arrow function binds no `this`, so one inside a method still reads the class. A `function` binds its own, so a `this` under one is reported, as is one in a computed key, a decorator or an `extends` clause, which read the scope around the class.
  - **The option is off by default,** so the rule alone still bans every `this`, and the config is where the repository relaxes it.
- **`typeof this` in a type isn't reported,** as in `m(): typeof this` or `y: typeof this.x`. It names a type and reads nothing at run time, so it carries none of the state the rule is about. A review of the first version found it reported.
- **`ReceiptStore` keeps its class** because it wraps Yjs's own stateful types, a `Y.Doc` and its `Y.Map`s, for React's `useSyncExternalStore`, as the owner decided on #83.
- **Its `this` needs no disable,** since `allowInClasses` allows it. The first version disabled `functional/no-this` line by line, 57 comments, because [`AGENTS.md`](../../AGENTS.md#definition-of-done) says to disable a rule only on the line it flags. A block disable around the class was the other choice, and needed an exception to that rule. `functional/no-classes` flags one line, so it's disabled on that line alone.
- **No module boundary for `scripts/lint/`.** The plugin imports nothing, and oxlint loads it by path from [`.oxlintrc.json`](../../.oxlintrc.json), so [dependency direction](dependency-direction.md) has nothing to check yet.
- **What it costs:** on 2026-11-24, `oxlint --deny-warnings` over the repository took about 380 ms without the plugin and between about 500 and 580 ms with it, the median of five runs in each of two sessions; all of `npm run lint` stayed between 2 and 2.6 s, within its run-to-run noise.

## What would reopen this

- **A principle an agent follows unprompted.** As models grow more capable, a principle they apply without being told becomes an instruction that only costs attention. Remove it then, and keep the rules its owning documents enforce.
- **A case a principle decides wrongly,** or two principles that pull apart in a way the precedence doesn't settle. Sharpen the principle's test, or add to the precedence, rather than listing the case.
- **A second class the owner wants to keep,** a wish to ban `this` inside an `Error` subclass again, or a class whose `this` should be reported after all.
- **oxlint's JS plugin API changing** in a way that breaks the plugin, or a built-in rule appearing that does the same job, which would replace it.
