# Types and schemas: reasons and decisions

Why the rules in [types and schemas](types-and-schemas.md) are as they are, and what was rejected. Read this only when changing or questioning one of them. Following the rules needs nothing from this file.

## Where a type lives

- **Decided by the owner** in review on [#42](https://github.com/DetweilerRyan/split/pull/42#discussion_r4649801912): "i'm not a big fan of making files just to hold types and/or their zod schemas. I prefer to leave types defined where their state is defined."
- **Reason:** a type beside the code that makes the value is read and changed together with it. A separate types file splits one change across two places.
- **Applied:** #42 moved `RoomId` from `src/types/roomId.ts` into `src/store/seedCodec.ts`. [#43](https://github.com/DetweilerRyan/split/issues/43) moved `src/types/receipt.ts` into `src/store/useReceiptStore.ts` and `src/types/seedSchema.ts` into `src/store/seedCodec.ts`, and deleted `src/types/`.
- **Not taken:** a shared `src/types/` folder, the layout the repository had before #42.
- **Amended on [#94](https://github.com/DetweilerRyan/split/issues/94): domain types live in `src/domain/`,** and the sync layer that builds their state imports them. The issue's body, which the owner keeps, says: "Amend it to say domain types live in `src/domain/`, and the store builds them." It followed the owner's question in the session on 2026-11-24, [recorded on #94](https://github.com/DetweilerRyan/split/issues/94#issuecomment-7121899237): "maybe store/ needs to be moved into domain??". `store/` mixed the receipt's rules with React, Yjs, the providers and browser storage, so it was split rather than moved, and the owner chose "Rename to src/sync/" for what remained, [recorded on #94](https://github.com/DetweilerRyan/split/issues/94#issuecomment-7122174375).
  - **Reason:** a type that states a business rule is read with that rule, not with the Yjs code that fills it in. In the store, a domain module such as `src/domain/receipt/math.ts` had to import its input type from the sync layer.
  - **Why types still don't get files of their own:** the reason from #42 holds. A type is read and changed with the code beside it, and the amendment only changes which code that is for a domain type: its rules, not the store that builds it. A types-only file in `src/domain/` would split one change across two places, as `src/types/` did.
  - **`RoomSnapshot` moved whole,** its `connection` and `peers` fields included, though they describe the sync layer's state. The issue's table put the type in `src/domain/receipt/`, and splitting it would change every component that takes a snapshot. Reopen it if the sync fields grow.
- **The seed schema's home was provisional, and #94 reopened it.** The owner chose `seedCodec.ts` "for now" in the session on 2026-11-21, [recorded on #43](https://github.com/DetweilerRyan/split/issues/43#issuecomment-7056479709); the alternative was a `src/store/receiptSeed.ts` holding the schema and `validateSeed`. On #94 the schema and `validateSeed` moved to `src/domain/receipt/receiptSeed.ts`, and `RoomId` with its parsing and creation to `src/domain/room/roomId.ts`. Compression, room URLs and hashes, and `hydrateFromSeed`, which writes into a Yjs doc, stayed in `src/sync/seedCodec.ts`.

- **Amended on [#134](https://github.com/DetweilerRyan/split/pull/134): a generic type helper goes in `src/utils/`,** one per file. #134 first copied `DeepReadonly<T>`, a deep-readonly type, into three property tests, since this rule bans a file of only types. The owner asked in [a review comment](https://github.com/DetweilerRyan/split/pull/134#discussion_r4690469589): "i'm thinking that frozen should be moved into a shared type utilty".
  - **Reason:** #42's reason is that a type is read and changed with the code that makes its value. A generic helper such as `DeepReadonly` describes no value of the app's and has no rules to sit beside, so it has no such code. Copies would drift instead. It's a type-level counterpart of a `src/utils/` function, and [code layout](code-layout.md)'s rule for that folder, a helper that knows nothing about receipts, money or rooms, fits it.
  - **Still not taken:** a shared types folder, or a file holding a domain type away from its rules.
  - **Named `DeepReadonly`,** not `Frozen`, its first name, as the owner asked in [a review comment](https://github.com/DetweilerRyan/split/pull/134#discussion_r4690506588): "let's rename this to DeepReadonly". The name says what it does: TypeScript's own `Readonly`, at every level instead of one.

## A schema owns its type

- **Decided by the owner** in the session on 2026-11-21, [recorded on #43](https://github.com/DetweilerRyan/split/issues/43#issuecomment-7056462985): "always use z.infer never duplicate a handwirtten type with it's zod schema. it is recommened that the inferred type be exported by the module so that callers don't have to use z.infer."
- **Reason:** a hand-written copy of a schema's type can drift from the schema, and the compiler won't notice when it does.
- **The export is recommended, not required,** in the owner's words.

## `type`, not `interface`

- **Decided by the owner** in the session on 2026-11-25, [recorded on #132](https://github.com/DetweilerRyan/split/issues/132#issuecomment-7149066406): "go with type, add it to 132".
- **Reasons:** unions, discriminated unions and `z.infer<…>` must be `type`s, so one keyword covers every type here. A `type` can't merge with another declaration of the same name by accident. An object `type` is assignable to `Record<string, unknown>`, which an `interface` isn't. What `interface` adds, `implements` and declaration merging, matters for class-based and published APIs, and this codebase is functions-first and not a library. Matt Pocock argues for `type` by default ([Total TypeScript](https://www.totaltypescript.com/type-vs-interface-which-should-you-use)).
- **Not taken: `interface`,** typescript-eslint's default and love's and antfu's choice. TypeScript's performance guide prefers `interface … extends` to `&`, since it caches interface relationships; `extends` reports an incompatible property where it's declared, where `&` gives `never`; and editors show an interface's name.
- **What would reopen it:** a deep `extends` hierarchy where checking gets slow. An `interface … extends` with a per-line disable and its reason covers that case.
- **Applied** on #132: 37 `interface`s, none with an `extends`, rewritten by oxlint's fixer.

## Ids and the strings built from them

- **Branded ids:** asked for by the owner on [#37](https://github.com/DetweilerRyan/split/pull/37#discussion_r4649349619) ("can we use a branded type or a string template type via zod to better type the key?"), filed as [#40](https://github.com/DetweilerRyan/split/issues/40) and done in #42. A brand stops a plain string, or a key built from an id, from being passed where an id is expected.
- **Which ids parse:** the owner chose, on [#40](https://github.com/DetweilerRyan/split/issues/40#issuecomment-7055361953), to accept only the forms the app has generated and to reject any other string. The patterns and that decision are documented in `src/domain/room/roomId.ts`.
- **Template literal keys:** from the same #37 question. A brand guards the id; a template literal type guards each key's shape, so `localStorage` and IndexedDB names can't be built from an unbranded string or with the wrong prefix. `src/sync/seedCodec.test.ts` pins this with `@ts-expect-error` checks.
- **Not taken:** `z.templateLiteral` schemas for the keys. The keys are built by the app, never parsed from input, so a type is enough.
- **Participant and item ids:** asked for by the owner in the session on 2026-11-24 ("i'm thinking we should brand participant ids"), filed as [#124](https://github.com/DetweilerRyan/split/issues/124). Participant ids enter from the Yjs document, a seed's roster and the saved identity in `localStorage`, and item ids from the document and a seed, yet they were plain strings. The owner's choices, [recorded on #124](https://github.com/DetweilerRyan/split/issues/124#issuecomment-7152388153):
  - **"Only today's format":** a participant id is `p-` and one or more words of letters, marks and digits joined by `-`, the form `participantId` mints since #100. Ids from the older ASCII-only rule, such as `p-jos`, have that form. `p-` on its own, which that rule gave a name with no ASCII letter or digit, doesn't. Not taken: any string starting `p-`, which would keep `p-` and the collisions #100 ended.
  - **"Leave it out, and log it":** a participant, item or saved identity whose id doesn't parse is left out of what the app reads, a participant's claims with it, with a console warning naming it. The Yjs document and `localStorage` aren't changed, so a later fix can still read them. Not taken: leaving it out silently, as the seed decoder does with a bad field, which hides lost data; and keeping it, which needs the unbranded string past the entry point.
  - **"Yes, same PR":** `ItemId` too, parsed at the same entry points. Item ids never had a format, since the app mints `item-<time>-<random>`, presets use `item-0`, and a seed may give any text up to 64 characters, so an item id is any non-empty string up to 64 characters. A seed's empty item id is still accepted and read as `item-<index>`, as before, so no seed valid before is refused, and the schema the MCP tool serves is unchanged.
  - **The rule lives beside `participantId`,** in `src/domain/receipt/roomSnapshot.ts`, which is pure; the warnings are logged in `src/sync/`, the shell, as [core and shell](code-design-principles.md#1-core-and-shell-keep-essential-logic-apart-from-the-machinery-around-it) asks.
  - **What it drops:** a participant stored as `p-`, minted only for a name with no ASCII letter or digit before #100, or under any other id that isn't one, with its claims; an item whose stored id, or its key where the id isn't text, is longer than 64 characters or empty; and a saved identity that isn't a participant id, such as `p-`, which then reads as no saved identity.

## Readonly by default

- **Asked for** on [#69](https://github.com/DetweilerRyan/split/issues/69): make immutability the default, sweep the code to it, and lint new code. Readonly types let TypeScript catch an accidental change to shared state, such as a snapshot's `items` or a prop's array, and tell a reader which values a function may change without reading its body.
- **Decided by the owner** in the session on 2026-11-24, [recorded on #69](https://github.com/DetweilerRyan/split/issues/69#issuecomment-7122175408): "Yes, all recommendations", which settled the issue's seven questions:
  1. types only (`readonly`, `Readonly<>`), plus `as const` on literal constants;
  2. readonly checked level by level, not deeply;
  3. local working arrays allowed inside a function;
  4. exemptions, such as Yjs and library types, as per-line disables with a reason;
  5. zod schemas get `.readonly()`, so `z.infer` is readonly;
  6. all of `app/`, `src/`, `scripts/` and `e2e/`, tests included;
  7. one pull request that sweeps the code and turns the rule on.

  The same comment: "It's a local oxlint JS plugin rule, the same mechanism as #83's, with no new dependency. `oxlint-tsgolint` isn't approved."

- **Not taken:**
  - **`oxlint-tsgolint`'s type-aware `prefer-readonly-parameter-types` and `prefer-readonly`,** which check a parameter deeply, through imported types. Not approved; it's a new package, and `--type-aware` turns on other rules too. The issue's trial found 134 findings with `ignoreInferredTypes` and `treatMethodsAsReadonly`. **Reversed on [#132](https://github.com/DetweilerRyan/split/issues/132)** for `prefer-readonly-parameter-types`, once [#120](https://github.com/DetweilerRyan/split/issues/120) had made lint type-aware with tsrs; see below.
  - **`eslint-plugin-functional`'s `type-declaration-immutability`,** through `jsPlugins`. It doesn't load under TypeScript 7, whose JS compiler API `ts-api-utils` reads.
  - **TypeScript and review only,** which leaves readonly to whoever remembers it.
  - **Runtime freezing** with `Object.freeze`, beyond `as const` and what zod's `.readonly()` does.
  - **Building working arrays with `map`, `filter` and `toSorted` only,** with no exemption for a local variable.
  - **A config-level exemption,** such as an `ignorePatterns` list, and **a rollout one directory at a time.**
- **How the rule itself works,** checking syntax level by level, how it treats `Readonly<…>`, mapped types and local variables, and what it skips, is in [its sidecar](../../scripts/lint/readonly.meta.md), which documents it apart from this repository. The owner asked for that on [#109](https://github.com/DetweilerRyan/split/pull/109#issuecomment-7139679143): "documents it's rules independenly of this project as if it where an external domain agnostic lint rule". Its design choices were made while writing it, under the owner's "pick the reversible default" for choices #69 left open.
- **zod's `.readonly()` also freezes the value it parses,** and JSON Schema marks a readonly schema `readOnly`. In the seed schema's JSON Schema, which the MCP tool `create_receipt_room` serves as its input, `readOnly` would tell a client the field is the server's and not to send it. So `immutable` in `src/domain/receipt/receiptSeed.ts` clears it with `.meta({ readOnly: undefined })`, and the schema the tool serves is unchanged; `receiptSeed.test.ts` checks both.
- **In-place `.sort` on a local working array stays.** The issue expected `participants.sort(...)` and `items.sort(...)` in the store to become `.toSorted`, but each sorts a local array the function has just built, which decision 3 allows. `toSorted` would also be the app's first ES2023 array method, which older browsers, such as Safari before 16, don't have.
- **Two checks, since [#132](https://github.com/DetweilerRyan/split/issues/132).** The owner chose "#69's options + allow libraries" and to keep `readonly/types`, [recorded on #132](https://github.com/DetweilerRyan/split/issues/132#issuecomment-7149201686). `prefer-readonly-parameter-types` sees through imported types, but only for parameters. `readonly/types` sees every type a file writes, such as a type alias, an interface's members and a return type, but only the levels written there. Neither replaces the other. Its hits, the `allow` list's reasons and the disables are in [the principles' sidecar](code-design-principles.meta.md#readonly-parameters).
- **The sweep, on [#69](https://github.com/DetweilerRyan/split/issues/69):** 487 findings when the rule was turned on. The mutable types that remain are each disabled on their line, with a reason: oxCrap's walks, which fill one list or set in place so deeply nested code keeps one stack frame per level, and a function's complexity, which `countRecursion` adds to through `parents`; oxCrap's cache of imported modules; and the provider cache and Liveblocks client on `globalThis`, which `src/sync/yjsProvider.ts` sets and its test deletes.

## Indexed reads and `!`

- **Asked for** on [#119](https://github.com/DetweilerRyan/split/issues/119), under _honest types_ in the [code design principles](code-design-principles.md#6-honest-types-let-the-types-rule-out-states-that-cant-happen): without `noUncheckedIndexedAccess`, `items[i]` is typed as a value even when `i` is past the end, so the type claims a value that may not be there.
- **Decided by the owner** in the session on 2026-11-24, [recorded on #119](https://github.com/DetweilerRyan/split/issues/119): "Yes, same PR". `typescript/no-non-null-assertion` was turned on outside tests in the same sweep, so the new errors couldn't be silenced with `!`. Tests are exempt, as from `max-nested-callbacks`, but the issue's "don't add `!`" holds for indexed reads in them too.
- **No casts either,** because [#117](https://github.com/DetweilerRyan/split/issues/117) bans `as` casts in the same round of work.
- **The sweep:** 114 errors in 30 files when the flag was turned on, counted on `main` at `485386e`; the issue's count of 99 in 26 files was from `4cd7cce`. Most became iteration, destructuring with a check, or `?.` in a test's assertion. Two kept a check for a case that can't happen through `computeReceiptMath`, a participant with no totals in `ParticipantCards` and the export text, because `perPerson` is a record keyed by id; `buildExportText` split its per-person lines into `personLines`, as its `@crap-allow` comment asked once it gained a branch, and lost that comment.
- **`satisfies` for `PRESETS`:** the annotation `Readonly<Record<string, ReceiptSeed>>` widened its keys to every string, so the tests' `PRESETS.plitvice` read as possibly missing. `satisfies` checks each seed against the same type and keeps the keys.
- **Vitest's `assert` in tests:** it narrows the type, as `expect(value).toBeDefined()` doesn't, and fails the test with its message when the value is missing.

## Checked, not asserted

- **Asked for** on [#117](https://github.com/DetweilerRyan/split/issues/117): a type assertion claims a type without checking it, so it's the main way around _honest types_' "parse input where it enters". The owner chose "Everywhere outside tests", [recorded on #117](https://github.com/DetweilerRyan/split/issues/117), including `scripts/oxcrap/`, whose AST narrowing becomes checks, keeping oxCrap's mutation score at its threshold.
- **Tests are exempt,** where a cast builds a fake. The end-to-end tests' and oxCrap's feature contract's screenplays count as tests: each reads its actor's notes back through one cast, the same in both.
- **oxCrap parses its AST fields rather than narrowing each node kind to oxc-parser's own types.** Those are interfaces, which TypeScript won't assign to `AstNode`'s index signature, so each walk would need a cast back. A parser that throws on a field oxc-parser always fills adds no branch to its caller, so no function's complexity rises and no mutant is left that only a malformed AST could kill.
- **What the sweep changed:** 95 assertions outside tests when the rule was turned on, counted on #117. A string name in an import or export, as in `export { T as 'a-b' }`, now names no table or function, where before it was read as `undefined`. A parse error in a coverage report now gives its error's name before its message. `decodeSeed` in `src/sync/seedCodec.ts` parses the whole seed with `receiptSeedSchema`, where it had checked only that `items` was an array, so a seed missing a field, such as `roster`, is now refused as no seed. The owner chose "Parse the whole seed" on [#128](https://github.com/DetweilerRyan/split/pull/128), accepting that.
- **Equivalent mutants:** the owner chose "Prove it in the type, else disable" on #128. Where a library's own type allows a value it never gives, as Ajv's `validate.errors` allows null after a failed validation, the fallback stays, with a Stryker disable saying why.
