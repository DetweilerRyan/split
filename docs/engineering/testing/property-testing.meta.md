# Property testing: reasons and sources

Why the rules in [property testing](property-testing.md) are as they are, where they come from, and what was rejected. Read this only when changing or questioning one of them. Following the rules needs nothing from this file.

## Where the rules came from

Asked for by the owner in [review on #71](https://github.com/DetweilerRyan/split/pull/71#discussion_r4668997580), where the first property test, oxCrap's complexity count, sat in `complexity.test.ts`:

- "i'm thinking that the property tests should be in their own test sidecar: *.property.test.ts";
- "also, let's make sure that property tests contribute to code coverage";
- "and, do we need a property testing doc with some basic guidance on when to write property tests?"

- **Their own sidecar,** so a reader can tell generated-input tests from examples. The name keeps them in the module's unit project, since both configs' patterns already match `*.test.ts`. No new project is needed.
- **Coverage:** checked on 2026-11-23 with a throwaway `src/` module tested only by a `.property.test.ts`. The test ran in the `unit` project, and the module's statement showed as covered in `coverage/coverage-final.json`.
- **Guidance in testing conventions at first, not a doc of its own:** that file was to hold everything needed to follow the testing conventions, and property tests are one more kind of Vitest test. Reversed on #154 once the file grew too large, as [Its own document](#its-own-document) says.
- **When to write one:** the cases where a property test earns its place are the ones a rule can be checked without repeating the code's own working. Round trips, invariants, a generator that knows the answer, and a simpler version to compare with are four such rules; the first two have candidates here in the seed codec and the receipt math.
- **Show it can fail, and keep constraints in the generators:** added after research on property testing with agents ([feedback](https://github.com/DetweilerRyan/split/pull/71#issuecomment-7108084420)). The owner said "yes, add both practices to 71".
  - **The pass that means nothing:** [Anthropic's study](https://www.anthropic.com/research/property-based-testing) of an agent writing property tests ([paper](https://arxiv.org/abs/2510.09907)) had its agent check "whether a pass is meaningful or trivial". In one case a property passed only because its body was wrapped in a try/except. With that removed, the test failed and exposed a real bug.
  - **Who judges:** an agent that writes a check shouldn't be the only judge of it. Breaking the code is a judgement the check makes itself. The oxCrap complexity property was checked this way: with catch clauses no longer counted, it failed.
  - **Constraints in generators, not filters, and no tautologies:** these are common practitioner guidance, for example in an [agent skill for property testing](https://skills.lc/ed3dai/ed3d-plugins/ed3dai-ed3d-plugins-plugins-ed3d-house-style-skills-property-based-testing-skill-md) and [developertoolkit.ai's workflow](https://developertoolkit.ai/en/workflows/test/property-based-testing.md).
  - **Also checked:** agentpatterns.io, which the owner named, was a placeholder with no pages on 2026-11-23. Research on properties drawn from a spec rather than from the code ([Spec-Driven PBT](https://arxiv.org/pdf/2611.15920)) supports the existing rule against working out the answer the way the code does.
- **Generate every way the input can be written, the dodges and look-alikes, and break each rule:** added on [#84](https://github.com/DetweilerRyan/split/pull/84), the owner saying "add all four to 84" ([feedback](https://github.com/DetweilerRyan/split/pull/84#issuecomment-7116049248)).
  - **The case:** oxCrap's lookup-table guard (#82) had a property test from the start. It checked that a switch moved into a table scores as it did, in one file, with no casts and nothing else touching the table. It passed on its first run and never failed.
  - **What it missed:** a fresh-context review then found five bugs: imported handlers, casts on the table, tables changed inside a function, writes counted as reads, and shadowing. Each sat in a decision the issue had made, and none of them was a dimension of the generator.
  - **What would have caught them:** after the owner asked whether the property tests caught anything, the generator gained where the table lives, casts, decoys and shadows. Undoing each fix then made it fail, each time with a minimal counterexample, and the shadowing dimension found the gap the review had left open.
  - **Why break each rule, and why mutation testing does most of it:** the first property had been shown to fail, but only by breaking the membership count, its central rule. That showed it had teeth for the claim, not for the decisions. The owner then asked "isn't point three covered by mutation testing?" ([feedback](https://github.com/DetweilerRyan/split/pull/84#issuecomment-7117550619)). The mutation report had mutants undoing three of the four fixes, each killed by the property test. It had none for the fourth, a cast on the table, since no mutator replaces `unwrap(node)` with `node`, so that one was checked by hand. The owner said mutation testing would be extended to the whole app ([#85](https://github.com/DetweilerRyan/split/issues/85)), and chose "narrow point 3": break by hand only what no mutant can undo.
  - **The second oracle,** "the answer for no pattern at all", made the decoys and shadows checkable without repeating `tables.ts`'s working: a changed table or a hidden read must score as a read of a name that isn't a table.
- **Their cost:** a property test runs its check once per input. oxCrap's complexity property runs 1,000 inputs in about 0.33 s, measured on 2026-11-25, since each is one parse of a small function.
- **Soak a new property, and keep what the soak finds as examples:** asked for by the owner on 2026-11-25: "when new property tests are added they should be run with very high thresholds so that edge cases can be fixed in the property test or fixed in the code. additionally, unit tests should be added for the failing property test outputs so that the unit tests can cover those cases even when the property tests are run at lower thresholds as they are in CI".
  - **Why soak:** CI runs a few hundred inputs per property to stay fast, so an edge case that turns up once in tens of thousands of inputs may first fail on an unrelated pull request, long after the property was written. A soak run before the commit finds it while the code and the property are still the author's focus.
  - **Why an example per failure:** after the soak, CI may never generate that input again. An example test checks it on every run, and the [example tests](property-testing.md#when-to-write-one) are also where a reader sees the hard cases. The [proptest README](https://docs.rs/crate/proptest/0.4.0/source/README.md) gives the same advice: commit the regression file and add the known input as its own unit test.
  - **Why the fault can be in the property:** a failure means the code and the property disagree, and either can be wrong. An example test with the right answer settles which one, whichever gets fixed.
  - **Prior art, searched on 2026-11-25:** no source names a one-off soak of a new property. The parts it combines are common: [Hypothesis profiles](https://hypothesis.readthedocs.io/en/latest/tutorial/settings.html) select a larger `max_examples` for CI or thorough runs through `HYPOTHESIS_PROFILE`, and proptest's [regression files](https://proptest-rs.github.io/proptest/proptest/failure-persistence.html) and Hypothesis's [`@example`](https://hypothesis.readthedocs.io/en/latest/reference/api.html) keep past failures running. [Goldstein et al.](https://cis.upenn.edu/~bcpierce/papers/icse24-pbt-in-practice) (ICSE 2024) found that Jane Street's engineers struggle to judge whether a property is effective, which the soak's report in the pull request partly answers.
  - **Three refinements, adopted by the owner on 2026-11-25** ("adopt all three and update the PR", [recorded on #154](https://github.com/DetweilerRyan/split/pull/154#issuecomment-7174761532)), after the session offered them from that research:
    - **A time budget, not a count.** The first version said 100,000 runs, or fewer if a run took over ten minutes, which meant guessing a property's speed. Why a budget, and how the script sets it, are in [the script's sidecar](../../../scripts/property-soak.meta.md#design).
    - **The input also goes in `examples`.** The example test checks the answer without the property; `examples` checks that the property still holds there, as Hypothesis's `@example` does. Checked: `examples` count towards `numRuns` (two examples with `numRuns: 3` ran three inputs), hence raising `numRuns` by their number.
    - **A comment saying where it came from,** after Hypothesis's `@example(...).via("regression test for issue #42")`, which exists so tools and people can tell a kept regression from a redundant example.
  - **Two minutes:** the owner, on 2026-11-25: "10 minutes is probably too long, let's go with 2 minutes and maybe reccomend that a subagent does it so that it doesn't block the agent from working" ([recorded on #154](https://github.com/DetweilerRyan/split/pull/154#issuecomment-7174979414)). Two minutes is still a soak: oxCrap's complexity property runs 1,000 inputs in about 0.33 s, and the helper's real test ran millions of cheap inputs a second, so two minutes is millions of inputs for a cheap property, and a property that takes 10 ms an input still runs about 12,000, over a hundred times fast-check's default.
  - **Soak by environment variable, in a background command:** an independent review of #154 found that a soak which edits the test file in the shared worktree collides with the Stop hook, which runs lint and tests on changed files, and that the subagent had no way to put an uncommitted file back. Offered an instruction to leave the file alone or a helper that reads the soak from the environment, and a subagent or a background command, the owner said: "use the env var helper, keep full treatment, just use a background command" ([recorded on #154](https://github.com/DetweilerRyan/split/pull/154#issuecomment-7176006746)).
    - **Why fast-check's global configuration:** the general reasons are in [the script's sidecar](../../../scripts/property-soak.meta.md#design). The first version replaced `fc.assert` with a `vi.doMock` of fast-check, which a second review found falls outside [Replacing external dependencies](unit-testing.md#replacing-external-dependencies). Asked about an exception, the owner asked: "does fast-check not have a standard approach for soaking property tests?" It does, a global `numRuns` from a setup file, which a property's own `numRuns` overrides. Only 7 of the 47 `fc.assert` calls outside the soak's own tests set one, counted with `git grep` on 2026-11-25, so the session recommended switching, and the owner said: "do it." ([recorded on #154](https://github.com/DetweilerRyan/split/pull/154#issuecomment-7177114258)). The cost is that those 7 can't be soaked without taking their `numRuns` out, and the rule to leave `numRuns` out of a new property until it has been soaked. A helper each test imported was turned down earlier too: it would break `oxcrap-self-contained` ([dependency direction](../dependency-direction.md#the-rules)), since oxCrap's property tests may import nothing from outside its folder.
    - **Why a background command:** the session keeps working while the soak runs, and reads the result when it finishes. Deciding where each fault is, and writing the examples, stays with the session that knows the code. Nothing touches a file, so the Stop hook and the session's own checks run on the property as written.
    - **Why coverage is off for a soak:** both configs write their coverage report on every run, and empty it first, so a soak with coverage on would replace the report oxCrap reads with one file's coverage.
  - **Every failure gets the full treatment, with a comment for where it was found:** the review noted that the first version applied the soak's steps to every failure without saying so, and that its comment fitted only a soak. The owner chose to keep the full treatment (as above), so the comment gains forms for CI and local runs.

## Checked by lint

- **Asked for by the owner on 2026-11-25:** "are there any lint rules that can help us write better property tests", then "open an issue to write our own lint plugin for property tests", which became [#155](https://github.com/DetweilerRyan/split/issues/155). No fast-check plugin exists for ESLint or oxlint, and Bun's `fast-check-no-unseeded-random` runs only in Bun, so the repository wrote its own, beside `functional.ts` and `readonly.ts`. Why each rule works as it does is in [its sidecar](../../../scripts/lint/property.meta.md).
- **The issue's open decisions, as #155's pull request took them:**
  - **All seven rules,** as the issue proposed.
  - **`.filter` only on a chain that starts with fast-check,** as proposed.
  - **No rule for an un-awaited async property:** `typescript/no-floating-promises` already reports one, as a warning that `--deny-warnings` makes fail. Checked on 2026-11-26 with a throwaway file.
  - **`example-origin` included,** since #154 made the `// Found by…` comment part of [Keeping a failing input](property-testing.md#keeping-a-failing-input).
  - **`predicate` asks for a call or a throw, not a call to `expect`:** four predicates in the lint plugins' own property tests assert through a helper, which a syntax rule can't see into.
- **The three filters the rule found were rewritten as constraints,** after the owner asked whether they could be ("will it be possible to refactor the three property tests such that they won't need the disable comments", then "do it and then soak the three property tests to be sure that they have not become flakey", [recorded on #157](https://github.com/DetweilerRyan/split/pull/157#issuecomment-7183444859)):
  - **`storedText`:** `fc.anything()` takes the leaf values it builds from, so given its defaults without strings it makes no string. The filter had dropped 9% of inputs (checked over 200,000 samples).
  - **`roomSnapshot`:** the empty prefix has a branch of its own, with a name whose first word isn't `p`, at the weight it had among the prefixes. `p` on its own, which that leaves out, joins `p-` as a constant.
  - **`receiptSeed`:** no generated id starts `item-`, which an empty id is stored as, so ids that `uniqueArray` keeps apart stay apart once stored. Only ids starting `item-` are lost, which a random 64-character string almost never is.
  - **Soaked for two minutes per property afterwards,** each property whose generator changed, with no failures.
