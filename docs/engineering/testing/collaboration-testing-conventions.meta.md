# Collaboration testing conventions: reasons

The reasons for [Collaboration testing conventions](collaboration-testing-conventions.md)' rules. Their sources are listed in [testing conventions' sidecar](testing-conventions.meta.md#sources).

## Split from testing conventions

- **Asked for by the owner on #159,** on 2026-11-26: "i'm beginning to think that the collaboration and contract tests belong in their own convention document. it's fairly complex and isn't relevant to every test. for example, it's not relevant to feature tests" ([recorded](https://github.com/DetweilerRyan/split/pull/159#issuecomment-7201496163)). Shown a name and trigger, the owner said: "go ahead and make the move".
- **A conventions document, not a kind's,** because its rules apply to any code that wires tested code: a container component, and a unit-tested module that wires stores or services. It names no kind of test.
- **The name** follows the index's `<topic>-conventions.md`. Not taken: `collaboration-and-contract-testing-conventions.md`, which is long, and `dependency-inversion-conventions.md`, which names the mechanism, not the tests, and the mechanism is core and shell's. A name that invites mocking, such as `mocking-conventions.md`, was also turned down: the document is mostly about not mocking until a test earns it.
- **The trigger and the opening use agents' own words.** The owner asked how likely a fresh agent is to recognise "collaborator" and follow the trigger. An agent thinks "mock the child components" or "dependency injection", not "fake a collaborator", so the index trigger and the opening name those, and testing conventions' `vi.mock` ban points here by name.
- **What stayed in testing conventions:** the exception for wiring code in "What a test checks", "Fake only what can't run" and its pointer to the fakes allowed here, and "Passing in isn't inverting", which is about passing any dependency in.

## Collaboration and contract tests

- **Asked for by the owner on #159,** on 2026-11-26, after the session asked whether `RoomView`'s one-off exception covered a third rule: "i'd prefer the rule be reworked such that RoomView is no longer an exception. do some web research for precedent on using dependency inversion to test react components (containers for lack of a better word) that are composed of other react components where we avoid writing redudent tests for the container component that are already covered by the tests for the components it's composed of" ([recorded](https://github.com/DetweilerRyan/split/pull/159#issuecomment-7196990346)). Shown the research and a proposed rule, the owner said: "it should be generalized in the testing-conventions.md doc and then made specific for the component-and-hook-testing doc. i'd like the rule to reference dependency inversion as the architectural mechanism and then feel free to barrow wording from any of the sources like collaboration test or contract test" ([recorded](https://github.com/DetweilerRyan/split/pull/159#issuecomment-7197356194)).
- **The terms are Rainsberger's.** A collaboration test checks whether a client uses its neighbours correctly, and a contract test whether a supplier behaves as its clients expect ([Who tests the contract tests?](testing-conventions.meta.md#rainsberger-contract-tests)); a client that stubs a supplier's answer calls for a contract test of that supplier ([Getting started with contract tests](testing-conventions.meta.md#rainsberger-getting-started)). He keeps the two in step by hand, which "Keep fakes and contract tests in step" asks too.
- **Where the rule's conditions come from:**
  - **Fake a third-party collaborator only at the edge:** "Only Mock Types You Own", from Freeman, Pryce, Mackinnon and Walnes ([Mock Roles, not Objects](testing-conventions.meta.md#mock-roles)), who test an object by replacing its neighbours with objects that check they're called as expected. They'd wrap a third-party type rather than fake it; the rule's "faked only at the edge" is this repository's existing rule for third parties.
  - **Split the code when the fakes grow too many:** the same paper's "Too Many Mocks", which reads them as a sign the object under test is too large.
  - **A test that runs the real collaborators:** Fowler, who says either style must be combined with coarser-grained tests ([Mocks Aren't Stubs](testing-conventions.meta.md#mocks-arent-stubs)), and who says he has "stayed with classic style", using doubles for awkward collaborations ([UnitTest](testing-conventions.meta.md#fowler-unit-test)).
  - **Wiring in the composing code, logic in tested collaborators:** Feathers' humble object keeps the untested layer to a thin wedge of delegation and tests the logic apart from it ([The Humble Dialog Box](testing-conventions.meta.md#humble-dialog-box)). It supports keeping a container thin; it doesn't itself test that thin layer, which the collaboration test adds.
- **Dependency inversion is the mechanism,** as the owner asked, and as _core and shell_ already names it in code design principles: the code declares the interface in its own terms, importing no value or type that implements it.
  - **Inversion, not just passing in:** typing a collaborator from the real one, as `RoomView` still does with `ComponentProps<typeof Header>`, is what Martin calls abstractions depending on details ([The Dependency Inversion Principle](testing-conventions.meta.md#martin-dip)); clients own the interfaces they use ([Placement of Abstract Factories](testing-conventions.meta.md#seemann-abstract-factories)); and "DI is about wiring, IoC is about direction, and DIP is about shape" ([DIP in the Wild](testing-conventions.meta.md#dip-in-the-wild)). Asked to choose, the owner said: "go with true inversion without RoomView's defaults so that it is true dependency inversion" ([recorded](https://github.com/DetweilerRyan/split/pull/159#issuecomment-7198387023)).
  - **No default, a composition root instead:** a default that imports the real implementation is what Seemann calls Bastard Injection ([Succeeding with Dependency Injection](testing-conventions.meta.md#seemann-succeeding-di)), and he wires real implementations in one composition root near the entry point ([Composition Root](testing-conventions.meta.md#seemann-composition-root)).
  - **Precedent in React is partial:** react-select types its `Option` slot as a component of `OptionProps`, the props it passes ([react-select components](testing-conventions.meta.md#react-select-components)), but imports that type from the real `Option`'s module and defaults to the real components. It's precedent for typing a slot by what's passed to it, not for no defaults; no React library the research found has a slot with no default.
  - **What the type checker sees:** TypeScript compares types by their members ([Type Compatibility](testing-conventions.meta.md#ts-type-compatibility)), and with `strictFunctionTypes`, which `strict` turns on in this repository's `tsconfig.json`, it compares a component's props strictly, so wiring a real part in at the composition root catches a new required prop or a changed type, but not a prop it's given and ignores. The contract tests cover that.
- **Stores and services are injected too:** asked whether `RoomView`'s services should be injected ([recorded](https://github.com/DetweilerRyan/split/pull/159#issuecomment-7199270146)), "i don't mean that we should pass hooks as props, that's bad practice, but i mean that the service as a 'store' can be passed as a prop", and shown research, the owner said: "go with your recommendation, drop the default and consider the store as dependency injected via a prop. i'd prefer that the store that RoomView expects be an interface. not all dependency injected stores (services) will be able to use a real in memory version of the store such as can be done with yjs" ([recorded](https://github.com/DetweilerRyan/split/pull/159#issuecomment-7199099995)).
  - **A prop, not context:** React's docs say to start by passing props, which make "the data flow explicit", before context ([Passing Data Deeply with Context](testing-conventions.meta.md#react-context)), and Kent C. Dodds says "Don't reach for context too soon!" ([Application State Management with React](testing-conventions.meta.md#kcd-state-management)). React Redux removed the `store` prop in v6 and brought it back in v7 because "Some users expressed concerns that working with context in unit tests was not sufficient" ([v7.0.1](testing-conventions.meta.md#react-redux-701)).
  - **Context is the other way to inject a store,** sharing "the store instance via React Context - not the store values themselves" ([Zustand and React Context](testing-conventions.meta.md#tkdodo-zustand-context)), advice for app code with a deep tree. A container one level below its composition root can take a prop, as React's docs advise first.
  - **A real implementation where the test can build one, a fake otherwise:** TanStack Query's testing guide builds a real client per test and intercepts the network ([Testing](testing-conventions.meta.md#tanstack-testing)). The owner's point is that not every store can run in memory, so the rule allows a fake that implements the interface where the test can't replace the effects under the real one; the real one's contract tests then check what the code relies on. The edge is the browser or third-party API itself, faked under "Fake only what can't run" with no contract tests; a repository wrapper around one is a service. A store or service is set apart from a collaborator because its own logic is the app's, which "Fake only what can't run" runs for real, while a collaborator's work is what a collaboration test exists not to repeat.
  - **No default, even for a browser global:** a default that imports the real implementation is the Bastard Injection anti-pattern Seemann names, so code design principles' "When two principles pull apart" says earned complexity's defaults don't apply to a dependency taken for a collaboration test. Code layout's browser-global default still holds for a hook, which isn't inverted for one.
  - **A mutable store prop fits React's rules:** they say "A component's props and state are immutable snapshots. Never mutate them directly" ([Components and Hooks must be pure](testing-conventions.meta.md#react-pure)). A store prop's identity stays the same, its methods run outside render, in event handlers and effects, and render reads it only through `useSyncExternalStore`, React's hook for subscribing to an external store, which says "If the underlying store has mutable data, return a new immutable snapshot" ([useSyncExternalStore](testing-conventions.meta.md#react-use-sync-external-store)), as `useReceiptStore` does.
- **Why slots and not hooks:** React's docs sanction components passed as props and children, like slots in other libraries ([Composition vs Inheritance](testing-conventions.meta.md#react-composition)), and forbid passing hooks as values, naming dependency injection through a hook prop as the thing not to do ([React calls Components and Hooks](testing-conventions.meta.md#react-rules-hooks)). So a container's slots are collaborators, and its hooks aren't.
- **The counter-position, weighed:**
  - **Testing Library** advises that "you should avoid mocking out components" in general, then that if you need to, Jest's mocking is the way; and, in a separate answer, that how a component tree breaks down is an implementation detail, a trade-off of value against cost ([React Testing Library FAQ](testing-conventions.meta.md#rtl-faq)). A `slots` prop makes that breakdown part of a container's interface, which is the cost the rule accepts, and only for a container whose job is wiring.
  - **React's docs** say that if you need to mock components for tests, it's better to mock the server, and usually more effective to test the app end to end ([React calls Components and Hooks](testing-conventions.meta.md#react-rules-hooks)). The rule keeps a test of the real composition for that reason.
  - **Kent C. Dodds** warns that mocking severs a test's connection to what it fakes ([The Merits of Mocking](testing-conventions.meta.md#merits-of-mocking)). The rule answers that worry with its conditions: only collaborators with contract tests are faked, fakes meet the interface the code declares, which the type checker checks the real collaborators against, and the real composition still runs in at least one test.
- **Precedent in practice is thin:** two posts do it directly, [8th Light's](https://8thlight.com/insights/dependency-injection-in-react) (2021-02-18) and [Wolt's](https://careers.wolt.com/en/blog/tech/injecting-hooks-into-react-components) (2023-03-31), and the research found no well-known codebase or style guide with it as policy. Researched on 2026-11-26.
- **`RoomView` met the rule with [#165](https://github.com/DetweilerRyan/split/issues/165):** it declares `RoomSlots`, `RoomConnection` and `RoomServices` in its own terms, with no defaults, and `LoadedRoomView`, in its own file, passes in the real ones. The Yjs document stays behind the store's `hydrateSeed`. `ShareModal`, `UnclaimedBanner`, `Toast` and `ItemList` gained the contract tests they lacked. Whether its slots should be regrouped around `RoomView`'s own concerns is still the open question #165 raised.
- **Reopen when:** fakes in collaboration tests let a broken composition pass, which the end-to-end tests would show.

## When a collaboration test earns its cost

- **Asked for by the owner on #159,** on 2026-11-26: "i'm a bit concerned that some of these new guidlines will result in complexity that hasn't been earned, please add a section to testing-convetions regarding the earned complexity princple (and any other relevant principles) namely how it relates to when the abstractions detailed in Collaboration and contract tests are employed" ([recorded](https://github.com/DetweilerRyan/split/pull/159#issuecomment-7200406868)).
- **A test through the real collaborators is the default,** because "What a test checks" already prefers one, and a collaboration test's fakes give up the confidence Testing Library and Kent C. Dodds warn about ([the counter-position](#collaboration-and-contract-tests)). The section names the conditions under which it pays: wiring code, collaborators with tests, and a test that would repeat theirs.
- **Each bullet applies a code design principle:**
  - **A current use, not an expected one,** and **undo it when it stops paying,** are _earned complexity_'s, including its "putting the duplication back costs less than bending the abstraction".
  - **The least powerful seam:** _least power_ ranks plain data before an interface passed in. React elements are plain objects that can be passed as props, which React likens to slots ([Composition vs Inheritance](testing-conventions.meta.md#react-composition)), so an element slot is a seam the code only places, never calls, with no interface beyond `ReactNode`; a component slot is an interface passed in.
  - **Narrow interfaces, and splitting the code when the fakes grow too many,** are interface segregation's and _deep modules_', and Freeman and Pryce's "Too Many Mocks" ([Mock Roles, not Objects](testing-conventions.meta.md#mock-roles)).
- **The parameters are earned as a set,** moved here from "Collaboration and contract tests", where it was the session's call after round 19.
- **Reopen when:** a collaboration test turns up where a test through the real collaborators would have been shorter, or the section keeps code from being inverted that the owner wanted inverted.
