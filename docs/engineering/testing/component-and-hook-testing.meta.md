# Component and hook testing: reasons and sources

Why the rules in [component and hook testing](component-and-hook-testing.md) are as they are, where they come from, and what was rejected. Read this only when changing or questioning one of them. Following the rules needs nothing from this file. The sources it cites are listed in [testing conventions' sidecar](testing-conventions.meta.md#sources).

Why component and hook tests run in a real browser, and why jsdom with React Testing Library wasn't taken, is in [testing conventions' sidecar](testing-conventions.meta.md#projects-and-file-names), beside the project table it decided.

These rules come from Kent's [Common mistakes with React Testing Library](testing-conventions.meta.md#common-mistakes) (2020), adapted to Vitest's browser API.

- **`userEvent` from `vitest/browser`, not `@testing-library/user-event`.** Kent's 2020 advice was "Use `@testing-library/user-event` over `fireEvent` where possible." His 2026 recommendation supersedes it for browser tests: use Vitest's built-in `userEvent` and don't add `@testing-library/user-event` ([user-event#1319](testing-conventions.meta.md#user-event-1319)).
- **`expect.element` instead of waits.** Kent: "use `find*` any time you want to query for something that may not be available right away", and "put side-effects outside `waitFor` callbacks and reserve the callback for assertions only." `expect.element` retries the way `find*` and `waitFor` do, so the rule becomes: no waits of your own, and actions outside the assertion.
- **Absence with `not.toBeInTheDocument()`.** Kent: "Only use the `query*` variants for asserting that an element cannot be found." Vitest's locators are lazy, so there's no `query*` variant; the negated assertion does that job.
- **No `act`.** Kent: "Learn when `act` is necessary and don't wrap things in `act` unnecessarily." `vitest-browser-react` uses `act` internally for rendering, and `userEvent` waits for the browser. `renderHook` returns its own `act` for calling a hook's functions.
- **Hooks through components.** Kent: "In most situations, this is how I would recommend testing this kind of a hook", and for complicated hooks `renderHook` "is more useful" than a hand-written test component, which must reimplement rerendering, unmounting and async waiting ([How to test custom React hooks](testing-conventions.meta.md#custom-hooks)). The post (2020) predates `renderHook` living in `vitest-browser-react`, but its reasoning carries over.
- **A container is `<Name>.tsx`, and its composition root `<Name>.root.tsx`,** as the owner chose on #169. In review the owner first proposed the container as `<component>.root.tsx` ([comment](https://github.com/DetweilerRyan/split/pull/169#discussion_r4721563160)), and invited push-back; the session pointed out that "root" already means the composition root in these documents. The owner then asked for it the other way round, and chose it ([recorded](https://github.com/DetweilerRyan/split/pull/169#issuecomment-7224190409)).
  - **`.root` reads like the other file infixes** (`.test`, `.meta`, `.browser`): the composition root is about its container, wiring it and holding no logic.
  - **The names reversed what the owner chose earlier,** when the composition root was `RoomView` and the container `RoomViewRoot`, so that "root" means one thing.
  - **A nested container has no root file,** since its parent's root binds it.
- **Slots, not parts,** as the owner asked in review: "we should probably use the term slots instead of parts to be more inline with the broader react community" ([comment](https://github.com/DetweilerRyan/split/pull/159#discussion_r4711932004)). MUI names the prop that takes the components a caller passes in `slots`, and React's docs liken elements passed as props, such as `left={<Contacts />}`, to "slots" in other libraries ([Composition vs Inheritance](https://legacy.reactjs.org/docs/composition-vs-inheritance.html)). `RoomView`'s prop was renamed in #165.
- **The container rule is in bullets,** as the owner asked: "this paragraph is quite long, should it be broken up into bullets?" ([comment](https://github.com/DetweilerRyan/split/pull/159#discussion_r4712124006)).
- **Layout is [Component layout](../component-layout.md)'s,** and its reasons are in [its sidecar](../component-layout.meta.md).
- **A container with only two slots has a collaboration test anyway,** for the room's items, because the owner asked for one: "consider splitting Items into it's own container with it's own collaboration test and it's own slots". Collaboration testing conventions would otherwise test it through its two real components.
- **A container's slots are faked in its collaboration test.** The owner decided this first for `RoomView`, on [#93](https://github.com/DetweilerRyan/split/issues/93#issuecomment-7122174580): "Each hook and component", and "but also you can test RoomView more easily if you dependency invert each of it's constituent parts via render props that can be easily mocked so that the test isn't redudant with the tests for the new sub components." It was an exception until #159, when the owner asked for a general rule, and chose true dependency inversion, with no default `parts`, over typing parts from the real ones, and then that the store it calls or hands its hooks be injected as an interface, with no default for `services` ([recorded](https://github.com/DetweilerRyan/split/pull/159#issuecomment-7199099995)); why that rule is as it is, and its sources, are in [collaboration testing conventions' sidecar](collaboration-testing-conventions.meta.md#collaboration-and-contract-tests).
  - **Its hooks aren't injected.** React's rules say "Never pass around Hooks as regular values" ([React calls components and hooks](https://react.dev/reference/rules/react-calls-components-and-hooks#never-pass-around-hooks-as-regular-values)), and the React Compiler relies on those rules to compile a component. So a container calls its real hooks, and its test checks a hook's work only far enough to tell which handler a slot's callback reached; each hook has a test of its own.
- **The stylesheet** makes `toBeVisible` reflect the app's real CSS (Tailwind, through PostCSS), so a hidden element can't pass as visible. The browser project's setup file loads it once, as the owner asked in review on #169 ([comment](https://github.com/DetweilerRyan/split/pull/169#discussion_r4715551136)): "should this css file be loaded globally in the vitest runner for the browser tests?" With the setup file disabled, a test fails, so it's needed; and a test that forgot the import used to fail only on visibility, with nothing saying why.
- **User-visible behaviour, not implementation details.** Kent defines implementation details as "things which users of your code will not typically use, see, or even know about". He names two users of a component, "End-users and developers", and says a test "should typically only see/interact with the props that are passed, and the rendered output" ([Testing Implementation Details](testing-conventions.meta.md#testing-implementation-details)). Vitest's component testing guide gives the same advice: test user-facing behaviour, not state or internals ([Vitest](testing-conventions.meta.md#vitest-component-testing)).
- **Tests run through the React Compiler.** Decided by the owner in the session on 2026-11-21: "add the @vitejs/plugin-react package to make sure the tests do run through React Compiler. memoisation can affect the results of tests." `next.config.ts` builds the app with `reactCompiler: true`.
  - **What changed:** `vitest.config.ts` runs `babel-plugin-react-compiler` first through `@vitejs/plugin-react`.
  - **Version:** 5.2.0, the newest release that supports the Vite 6 inside Vitest 5.0.5, since 6.x needs Vite 8.
  - **Guard:** `vitest.config.browser.test.ts` checks a component compiles to the compiler's memo cache (`const $ = _c(<slots>)`). With the plugin line removed it fails, and every other test still passes.
  - **Reopen when:** Vitest moves to Vite 8; plugin-react can then move to 6.x.
  - **The case that showed why it matters:** with the compiler on, it memoized a `localStorage` read in `useActiveIdentity` on inputs that didn't include storage. See [#37](https://github.com/DetweilerRyan/split/pull/37#discussion_r4649234960).
