# Testing conventions: reasons and sources

Why the rules in [testing conventions](testing-conventions.md) are as they are, where they come from, and what was rejected. Read this only when changing or questioning one of them. Following the conventions needs nothing from this file.

Most of the advice comes from Kent C. Dodds. Each source below was opened and checked against what is attributed to it on 2026-11-20 or 2026-11-21, apart from those for collaboration and contract tests, checked on 2026-11-26.

## What a test checks

Why a component test checks only what a user can see and do moved with the rule to [component and hook testing's sidecar](component-and-hook-testing.meta.md).

- **Query order** comes from Kent's [Common mistakes with React Testing Library](#common-mistakes) (2020), and follows Testing Library's [query priority](#query-priority): `getByRole` first, test IDs last. Kent says to use `*ByRole` "most of the time", and to query "by the _actual_ text" rather than test IDs. Vitest's locators keep the same names except `getByPlaceholder` (Testing Library's `getByPlaceholderText`). Vitest has no `getByDisplayValue`, so it's left out of the order. Playwright names the label locator `getByLabel`, so the rule names both.
- **Use the code the way it's really used.** "The more your tests resemble the way your software is used, the more confidence they can give you", and Kent endorses Guillermo Rauch's "Write tests. Not too many. Mostly integration." ([The Testing Trophy](#testing-trophy)). The exception for collaborator-free logic is this repository's own: functions like `computeReceiptMath` have many edge cases that are clearest tested directly.
- **Specific assertions.** "Make assertions specific" and "Tests should resemble users" are two of [Epic Web's principles](#epic-web-principles). The Epic Stack's `epic-testing` skill shows the good-and-bad example pattern each kind's document uses ([epic-testing](#epic-testing)). It was written by a contributor and merged by Kent, so its wording isn't his.
- **Test files are exempt from `max-nested-callbacks`.** Decided by the owner on [#76](https://github.com/DetweilerRyan/split/issues/76), on 2026-11-24: "Tighter, tests exempt", with `max-depth` 3 and `max-nested-callbacks` 3 everywhere else. A test's callbacks nest by structure, not by logic: a property test is already three deep at `describe`, `it` and `fc.property`, so a fourth callback inside it, such as an `arbitrary.map`, would fail. When the rule was turned on, every place it flagged was in a test file. Flattening them would move a test's setup away from the property it serves.
  - **Not taken:** the issue's other options, ESLint's default limit of 10, which nothing broke, or a limit test files fit.
  - **What would reopen it:** a test whose nesting hides its logic, rather than its structure.

## Projects and file names

Why the `unit` project has no layout assertions moved with the rule to [unit testing's sidecar](unit-testing.meta.md).

Why tests run through the React Compiler moved with the rule to [component and hook testing's sidecar](component-and-hook-testing.meta.md).

- **Component and hook tests run in a real browser.** Decided by the owner on [#38](https://github.com/DetweilerRyan/split/issues/38#issuecomment-7053714472) ("approved"), choosing Vitest Browser Mode over jsdom with React Testing Library.
  - **Kent:** in 2026 he recommends Vitest's or Playwright's built-in user events and locators for new browser tests, and moving important interaction tests to a real browser rather than relying more on simulated events ([user-event#1319](#user-event-1319)).
  - **Courses and tools:** his Epic Web workshop teaches Browser Mode, with a section titled "Sunsetting JSDOM" ([Epic Web workshop](#epic-web-workshop)). Vitest calls Browser Mode "the recommended approach for component testing" ([Vitest](#vitest-component-testing)).
  - **Not taken:** jsdom with React Testing Library. It's cheaper to set up, but it keeps testing in the simulated DOM Kent and Vitest are moving away from, and it would need `@testing-library/user-event`, which is no longer getting feature work. The trial and comparison are on #38.
- **`<module>.browser.test.ts(x)` names browser tests.** Decided by the owner on #38: "go with `<module>.browser.test.ts(x)`". The alternative was choosing the project by folder (`src/components/`, `src/hooks/`). A suffix keeps the file a sidecar and shows the environment in its name.
- **`<module>.real.test.ts` names tests that run real programs or touch the file system.** Asked for by the owner in review on [#39](https://github.com/DetweilerRyan/split/pull/39#discussion_r4649529184), who suggested `.real.test.ts` and asked for precedent.
  - **The distinction:** Google's _Software Engineering at Google_ separates a test's size, "the resources that are required to run a test case", from its scope, "the specific code paths we are verifying" ([test size and scope](#swe-test-sizes)). A small test "must run in a single process" and isn't "allowed to access the network or disk". A medium test "can span multiple processes" but reaches no system other than `localhost`.
  - **Where `prepare-sandbox` falls:** its test is narrow in scope, one script, but medium in size: it runs subprocesses and writes files.
  - **Why not `.integration.test.ts`:** it's what a Vitest maintainer suggests for separating such tests, with projects named `unit` and `integration` and files `**/*.unit.test.ts` and `**/*.integration.test.ts` ([Vitest discussion #4675](#vitest-4675)). But "integration" names scope, so it would mislabel a narrow test.
  - **Precedent:** `.real.` names the size property, and matches the `_real.py` tests in the owner's market-research repository, which use real binaries and loopback without the internet.
  - **Not taken:** Google's own `.medium.test.ts`, a term readers would have to look up.

## Mocking

- **Fake only what can't run, at the edge.** Kent: "Mocking severs the real-world connection between what you're testing and what you're mocking", and the payoff is "usually practicality". In UI tests, "I never make actual network calls." On speed: "trading confidence for a minute or two faster test suite is a bad trade" ([The Merits of Mocking](#merits-of-mocking)).
- **Never mock React's hooks.** Kent: "You throw away a LOT of confidence in doing so" ([How to test custom React hooks](#custom-hooks)).
- **`vi.mock` for directly imported third-party modules.** A repository rule, kept because `yjsProvider.ts` imports Liveblocks, `y-webrtc` and `y-indexeddb` directly. Passing them in would change its public interface for tests alone. A strict no-mocks rule, as market-research has, was not taken because it would contradict that existing test.

## Collaboration and contract tests

- **Asked for by the owner on #159,** on 2026-11-26, after the session asked whether `RoomView`'s one-off exception covered a third rule: "i'd prefer the rule be reworked such that RoomView is no longer an exception. do some web research for precedent on using dependency inversion to test react components (containers for lack of a better word) that are composed of other react components where we avoid writing redudent tests for the container component that are already covered by the tests for the components it's composed of" ([recorded](https://github.com/DetweilerRyan/split/pull/159#issuecomment-7196990346)). Shown the research and a proposed rule, the owner said: "it should be generalized in the testing-conventions.md doc and then made specific for the component-and-hook-testing doc. i'd like the rule to reference dependency inversion as the architectural mechanism and then feel free to barrow wording from any of the sources like collaboration test or contract test" ([recorded](https://github.com/DetweilerRyan/split/pull/159#issuecomment-7197356194)).
- **The terms are Rainsberger's.** A collaboration test checks whether a client uses its neighbours correctly, and a contract test whether a supplier behaves as its clients expect ([Who tests the contract tests?](#rainsberger-contract-tests)); a client that stubs a supplier's answer calls for a contract test of that supplier ([Getting started with contract tests](#rainsberger-getting-started)). He keeps the two in step by hand, which "Keep the two in step" asks too.
- **Where the rule's conditions come from:**
  - **Fake only collaborators the repository owns:** "Only Mock Types You Own", from Freeman, Pryce, Mackinnon and Walnes ([Mock Roles, not Objects](#mock-roles)), who test an object by replacing its neighbours with objects that check they're called as expected. They'd wrap a third-party type rather than fake it; the rule's "faked only at the edge" is this repository's existing rule for third parties.
  - **Split the code when the fakes grow too many:** the same paper's "Too Many Mocks", which reads them as a sign the object under test is too large.
  - **A test that runs the real collaborators:** Fowler, who says either style must be combined with coarser-grained tests ([Mocks Aren't Stubs](#mocks-arent-stubs)), and who says he has "stayed with classic style", using doubles for awkward collaborations ([UnitTest](#fowler-unit-test)).
  - **Wiring in the composing code, logic in tested collaborators:** Feathers' humble object keeps the untested layer to a thin wedge of delegation and tests the logic apart from it ([The Humble Dialog Box](#humble-dialog-box)). It supports keeping a container thin; it doesn't itself test that thin layer, which the collaboration test adds.
- **Dependency inversion is the mechanism,** as the owner asked, and as _core and shell_ already names it in code design principles: the code declares the interface in its own terms, importing nothing from what implements it.
  - **Inversion, not just passing in:** typing a collaborator from the real one, as `RoomView` still does with `ComponentProps<typeof Header>`, is what Martin calls abstractions depending on details ([The Dependency Inversion Principle](#martin-dip)); clients own the interfaces they use ([Placement of Abstract Factories](#seemann-abstract-factories)); and "DI is about wiring, IoC is about direction, and DIP is about shape" ([DIP in the Wild](#dip-in-the-wild)). Asked to choose, the owner said: "go with true inversion without RoomView's defaults so that it is true dependency inversion" ([recorded](https://github.com/DetweilerRyan/split/pull/159#issuecomment-7198387023)).
  - **No default, a composition root instead:** a default that imports the real implementation is what Seemann calls Bastard Injection ([Succeeding with Dependency Injection](#seemann-succeeding-di)), and he wires real implementations in one composition root near the entry point ([Composition Root](#seemann-composition-root)).
  - **Precedent in React is partial:** react-select types its `Option` slot as a component of `OptionProps`, the props it passes ([react-select components](#react-select-components)), but imports that type from the real `Option`'s module and defaults to the real components. It's precedent for typing a slot by what's passed to it, not for no defaults; no React library the research found has a slot with no default.
  - **What the type checker sees:** TypeScript compares types by their members ([Type Compatibility](#ts-type-compatibility)), and with `strictFunctionTypes`, which `strict` turns on in this repository's `tsconfig.json`, it compares a component's props strictly, so wiring a real part in at the composition root catches a new required prop or a changed type, but not a prop it's given and ignores. The contract tests cover that.
- **Why parts and not hooks:** React's docs sanction components passed as props and children, like slots in other libraries ([Composition vs Inheritance](#react-composition)), and forbid passing hooks as values, naming dependency injection through a hook prop as the thing not to do ([React calls Components and Hooks](#react-rules-hooks)). So a container's parts are collaborators, and its hooks aren't.
- **The counter-position, weighed:**
  - **Testing Library** advises that "you should avoid mocking out components" in general, then that if you need to, Jest's mocking is the way; and, in a separate answer, that how a component tree breaks down is an implementation detail, a trade-off of value against cost ([React Testing Library FAQ](#rtl-faq)). A `parts` prop makes that breakdown part of a container's interface, which is the cost the rule accepts, and only for a container whose job is wiring.
  - **React's docs** say that if you need to mock components for tests, it's better to mock the server, and usually more effective to test the app end to end ([React calls Components and Hooks](#react-rules-hooks)). The rule keeps a test of the real composition for that reason.
  - **Kent C. Dodds** warns that mocking severs a test's connection to what it fakes ([The Merits of Mocking](#merits-of-mocking)). The rule answers that worry with its conditions: only collaborators with contract tests are faked, fakes meet the interface the code declares, which the type checker checks the real collaborators against, and the real composition still runs in at least one test.
- **Precedent in practice is thin:** two posts do it directly, [8th Light's](https://8thlight.com/insights/dependency-injection-in-react) (2021-02-18) and [Wolt's](https://careers.wolt.com/en/blog/tech/injecting-hooks-into-react-components) (2023-03-31), and the research found no well-known codebase or style guide with it as policy. Researched on 2026-11-26.
- **`RoomView` doesn't meet the rule yet:** it types its parts from the real ones and defaults to them, its composition root shares its file, and `ShareModal`, `UnclaimedBanner`, `Toast` and `ItemList` have no tests of their own, so they have no contract tests; [#165](https://github.com/DetweilerRyan/split/issues/165) covers it.
- **Reopen when:** fakes in collaboration tests let a broken composition pass, which the end-to-end tests would show.
