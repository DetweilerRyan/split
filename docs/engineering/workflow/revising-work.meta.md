# Revising work: reasons

Why [revising work](revising-work.md) says what it does. Read this only when changing or questioning a rule there. Following the procedure needs nothing from this file.

- **The pull request is the record, even for feedback given in a session.** On 2026-11-21 the owner gave five rounds of feedback on [#47](https://github.com/DetweilerRyan/split/pull/47) in the session that wrote it, not on GitHub. Each round changed the pull request, but the only trace on it was a rewritten description, so a later session could see the result and not the request, nor tell the owner's decisions from the session's own. The owner asked for this procedure, and for the feedback to be backfilled as comments on #47.
- **A request in the session is feedback, and `AGENTS.md` says so.** On 2026-11-22, after [#57](https://github.com/DetweilerRyan/split/pull/57) was marked ready, the owner made five requests in the session: two approvals, a sidecar, a VS Code extension, and a choice of folder.
  - **What went wrong:** the session made each change but recorded none on the pull request. It treated them as new tasks or approvals rather than feedback, read this procedure only when an inline review comment arrived, and backfilled the five as comments when the owner asked ([the owner's feedback](https://github.com/DetweilerRyan/split/pull/57#issuecomment-7073836236)).
  - **The trigger was already in the workflow index,** so the miss was in recognising the trigger, not in finding the procedure.
  - **Why `AGENTS.md`:** it was the second time, after #47. The owner asked for a guard that a fresh session can't miss: "i do want the guard because i don't wan't this to happen again with a new fresh session". `AGENTS.md` is the one file every session loads, and the [engineering index](../README.md#adding-a-procedure) allows a boundary there when the owner asks for it to be loaded in every session.
  - **The same definition in three places** (the boundary, the index row, and this procedure's opening) is a pointer and a trigger, not a copy. The procedure owns the definition, and the other two name it so it is recognised.
- **Record before acting.** A session can end partway through a change. A request recorded first can be resumed; one held only in the conversation is lost with it.
- **Comments hold the history, the description holds the present.** The owner reads the description to decide what to look at ([submitting work](submitting-work.md#what-the-description-carries)), so it has to describe the pull request as it is. Putting the history in the comments too keeps it from being one fact in two places ([single source of truth](../../prose/single-source-of-truth.md)).
- **A pull request comment has no thread.** GitHub threads only inline review comments, so a response to a pull request comment is a new comment that links to it.
- **Named for the stage.** `revising-work.md` follows the `<verb>-work.md` names in the [workflow index](README.md). The owner's first wording was "receiving feedback", but the procedure is what the session does with feedback, which is revising the work.
- **Review again before pushing.** The owner asked for this on [#47](https://github.com/DetweilerRyan/split/pull/47#discussion_r4653484196) on 2026-11-21. The review reads the whole branch because a revision made for one comment can break what an earlier commit did. The reply comes after the push so that the commits it names exist on the remote.
